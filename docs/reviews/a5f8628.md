## Summary

**The change is correct.** It fixes a real bug, the mechanism it uses is the right
one, and I verified the behaviour it claims rather than taking the commit message's
word for it.

The bug was real: `-v` was declared only on the top-level parser, and argparse binds
a top-level optional strictly *before* the subcommand token. `agents up -v` — the
exact form `README.md:25` tells a new user to run — exited 2 with
`unrecognized arguments: -v`.

The fix declares `-v/--verbose` a second time on a shared `add_help=False` parent
parser and threads it into all four subparsers via `parents=[common]`. The subcommand
copy uses `default=argparse.SUPPRESS`, which is the load-bearing detail: when `-v` is
absent after the subcommand, `_SubParsersAction` never sets `verbose` in the
subnamespace, so it cannot overwrite a `-v` that was given *before* the subcommand.
Without `SUPPRESS`, `agents -v status` would have silently regressed to
`verbose=False`. The commit message calls this out and it is accurate.

Verified directly, on both interpreters present on this machine (CPython 3.11.12 and
3.12.10 — the `SUPPRESS`/subnamespace interaction is the kind of argparse detail that
is worth pinning to a version, so I checked):

```
['-v', 'status']                  -> verbose=True
['status', '-v']                  -> verbose=True
['status']                        -> verbose=False
['-v', 'status', '-v']            -> verbose=True
['events', '-v', '--limit', '5']  -> verbose=True, limit=5
['events', '--limit', '5', '-v']  -> verbose=True, limit=5
['up', '-v'] / ['stop', '-v']     -> verbose=True
['-v'] / []                       -> exit 2 (command still required)
```

End-to-end smoke test, not just the parser:

```
$ .venv/bin/python -m agents.cli status -v     # exit 0, renders
$ .venv/bin/python -m agents.cli events -v --limit 2   # exit 0, renders
```

Two incidental improvements worth noting as good: extracting `build_parser()` out of
`main()` makes the parser testable without invoking side effects, and the new test
asserts the negative case (`["status"]` → `False`), which is what actually guards
against a `SUPPRESS` regression.

The three findings below are all **low** severity. None of them is a defect in the
shipped behaviour; they are durability and hygiene issues. I am recording them rather
than padding the review — if you only read the summary, the takeaway is that this
commit is good.

## Finding 1 — `-v` parity is opt-in per subcommand, and nothing enforces it

**What:** Post-subcommand `-v` works only for subparsers that remember to pass
`parents=[common]`. All four current subcommands do. The fifth one somebody adds
next will not, unless they notice the pattern, and the failure is a hard `exit 2`
rather than a silently-ignored flag.

**Where:** `agents/cli.py:71-76` (the four `add_parser(...)` calls), `agents/cli.py:65-66`
(the `common` parent)

**Severity:** low

**Why it matters:** This is the exact bug the commit just fixed, re-armed for the next
subcommand. Reproduced with the real parser shape:

```python
s.add_parser('up', parents=[common])
s.add_parser('doctor')          # future subcommand, author forgets parents=
p.parse_args(['doctor', '-v'])
# agents: error: unrecognized arguments: -v   -> exit 2
```

The new test iterates a hardcoded tuple of argv lists, so it would stay green while
`agents doctor -v` was broken. Nothing — not a test, not a type, not a lint rule —
connects "is a subcommand" to "accepts `-v`".

The cheap structural fix is to make the invariant unforgettable rather than
documented, e.g. a local closure so there is no second way to add a subcommand:

```python
def _sub(name: str, help: str) -> argparse.ArgumentParser:
    return sub.add_parser(name, help=help, parents=[common])
```

and, on the test side, driving the assertions off
`parser._subparsers._group_actions[0].choices` so new subcommands are covered
automatically instead of by hand.

**Not applied.** `agents/cli.py` is outside my write scope (`casino/`, `docs/reviews/`).

## Finding 3 — The test's loop reports the wrong argv on failure

**What:** The three positive cases are asserted inside a bare `for` loop with no
parametrisation and no message, so a failure reports `assert False is True` without
saying which invocation broke.

**Where:** `tests/agents/test_cli.py:34-35`

```python
for argv in (["-v", "status"], ["status", "-v"], ["events", "-v", "--limit", "5"]):
    assert build_parser().parse_args(argv).verbose is True
```

**Severity:** low

**Why it matters:** These three cases fail for *different* reasons — `["-v", "status"]`
breaking means the `SUPPRESS` default regressed, `["status", "-v"]` breaking means
`parents=[common]` was dropped. Collapsing them into one anonymous loop throws away
that signal at exactly the moment you want it. `@pytest.mark.parametrize("argv", [...])`
gives three named cases for the same line count — and would put the already-imported
`pytest` to work. Adding `["up", "-v"]` and `["stop", "-v"]` would also close the gap
where two of the four subcommands are currently unexercised.

Separately: `main()` itself still has no test. `build_parser()` is now well covered, but
the `args.verbose` → `_setup_logging` → dispatch path is not, so a future refactor that
renamed the `verbose` dest would pass the parser test and fail at runtime. Noted, not
scored as its own finding — it is pre-existing, not introduced here.

**Not applied.** `tests/` is outside my write scope.
