## Verdict

The change is sound. It tests the right things, and the assertions it makes are the ones
that would actually catch a regression. The findings below are one real side effect plus a
handful of low-severity redundancies — none of them make the commit wrong.

**Verified claims from the commit message:**

- "73.3% to 100% line coverage" — accurate. `casino/cards.py` is 15 statements; the four
  previously-missed lines are exactly `Card.__repr__`'s return, the two `Deck.__init__`
  lines, and `Deck.draw`'s return (11/15 = 73.3%). Re-measured after the change:
  `casino/cards.py 15 stmts, 0 miss, 100%`.
- "asserted as a multiset so card ordering stays free" — accurate. Composition tests use
  `Counter`/`set` over `(rank, suit)` projections; only `test_deck_is_shuffled_on_construction`
  depends on order, and it depends on it deliberately.
- "shuffle behaviour is exercised via `random.seed` rather than by asserting on any
  particular chance outcome" — accurate in intent, but see Finding 1 for the cost.

**Things I specifically checked and found correct:**

- The repr parametrization covers all four suits. This matters more than it looks:
  `__repr__` keys on `suit[0].upper()`, so the test is really asserting that
  hearts/diamonds/clubs/spades have distinct initials. They do. A fifth suit sharing an
  initial would be caught here.
- `test_deck_is_shuffled_on_construction` is a genuine regression detector, not a tautology.
  Delete `random.shuffle` from `Deck.__init__` and it fails deterministically.
- `test_multi_deck_contains_each_combination_once_per_deck` correctly separates the two
  claims (`set(dealt)` for the combinations, `set(dealt.values()) == {3}` for the count)
  rather than conflating them into one `Counter` comparison.
- The `in` / `not in` assertions in the draw tests rely on `Card`'s default identity
  equality. For a single deck that is correct and unambiguous.

## Finding 1 — Tests leave the global RNG seeded, leaking deterministic state into every later test

**Where:** `tests/test_cards.py:53, 59, 61, 67, 69, 75, 88` (every `random.seed(...)` call)
**Severity:** medium

Six tests call `random.seed(...)` on the process-global `random` module and none of them
restore the prior state. `casino.cards.Deck` uses module-level `random.shuffle`, so seeding
globally is the natural way to make it deterministic — but the seed outlives the test.

Demonstrated: I added a throwaway probe test that prints `random.random()` and ran it two ways.

```
probe alone:                    0.03198791604838647   (varies per run)
probe after test_cards.py:      0.60170447277744      (identical across runs)
probe after test_cards.py:      0.60170447277744
```

Anything scheduled after this file inherits a pinned RNG. Concretely, that means:

- A future `tests/test_table.py` asserting a statistical property over N simulated rounds
  would silently depend on whether `test_cards.py` ran first — and would pass or fail based
  on test *ordering*, not on the code under test. This is exactly the kind of failure that
  costs a day to diagnose.
- There is no `pytest.ini`, `pyproject.toml`, or `setup.cfg` in the repo, so there is no
  seed-management plugin (`pytest-randomly` et al.) mitigating this today.

The fix is to scope the seeding rather than broadcast it — e.g. a fixture that snapshots
`random.getstate()` and restores it in teardown, or `monkeypatch.setattr(casino.cards,
"random", random.Random(seed))` to avoid touching global state at all.

**Not fixed:** the fix belongs in `tests/`, which is outside my write scope.

## Finding 2 — Three of the six seeds are decorative; they add leakage without adding determinism

**Where:** `tests/test_cards.py:75` (`random.seed(99)`), `tests/test_cards.py:88` (`random.seed(2024)`)
**Severity:** low

In `test_draw_returns_a_card_and_removes_it_from_the_deck` and
`test_drawing_the_whole_deck_yields_every_card_exactly_once`, no assertion depends on the
shuffle order. The first checks membership and length; the second checks a multiset and an
empty list. Both hold for *every* permutation. The seeds buy nothing and are pure cost under
Finding 1. Worth dropping when Finding 1 is addressed.

## Finding 3 — Two tests assert CPython RNG properties rather than `Deck` behaviour

**Where:** `tests/test_cards.py:58-71` (`test_same_seed_produces_same_deck_order`,
`test_different_seeds_produce_different_deck_orders`)
**Severity:** low

"Same seed → same sequence" and "different seeds → different sequences" are guarantees of
the Mersenne Twister, not of `Deck`. `Deck.__init__` is a deterministic list comprehension
plus one `shuffle` call; given the stdlib guarantee, these tests cannot fail unless
`test_deck_is_shuffled_on_construction` also fails. They are redundant with a test that is
already present and stronger.

Minor secondary risk: `test_different_seeds_produce_different_deck_orders` would be a flaky
test if the seeds were ever parameterized or randomized, since two seeds *may* legitimately
collide. Pinned at 1 and 2 it is safe, but the shape invites future breakage.

## Finding 4 — `test_single_deck_has_52_cards` is subsumed by the parametrized size test

**Where:** `tests/test_cards.py:32-33`
**Severity:** low

`test_deck_size_scales_with_num_decks[1]` asserts `len(Deck(1).cards) == 52 * 1`. The only
distinction is `Deck()` vs `Deck(1)`, i.e. default-argument coverage — which is real but
incidental, and is already exercised by four other tests that call `Deck()` bare.

## Finding 5 — `test_draw_from_empty_deck_raises` pins a `list.pop` implementation detail as the deck's contract

**Where:** `tests/test_cards.py:96-101`
**Severity:** low

`Deck.draw` is `return self.cards.pop()`, so the `IndexError` is leaked from the underlying
list, not chosen as a deck-exhaustion contract. Asserting on it is defensible as a
characterization test, but it now blocks the natural evolutions of this API — raising a
domain error, or auto-reshuffling the discard pile — without a corresponding test update.

No live defect follows from this: `Table.play_round` builds a fresh `Deck` per round and a
hand busts well before 52 cards, so exhaustion is unreachable in the current simulator.
Flagging the coupling, not a bug.

## Observation — `Card` has no `__eq__`/`__hash__`, and the tests work around it

**Where:** `casino/cards.py:7-13`; workarounds throughout `tests/test_cards.py`
**Severity:** low (observation, not a defect in this commit)

Every composition assertion in the new file projects cards to `(c.rank, c.suit)` tuples
before comparing. That is the correct thing to do given today's `Card`, and I am noting it
only because the repetition is evidence of a gap in the production type: `Card` is a value
object with identity semantics.

I deliberately did **not** fix this. Adding `__eq__`/`__hash__` would change comparison
semantics for `Hand` and `Table` as well, which makes it a design change rather than the
low-risk correction this review is scoped to. It also wants a decision about whether two
`Card("A", "hearts")` from a six-deck shoe should compare equal. Raising it for a future
change, with a spec.
