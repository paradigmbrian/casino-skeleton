## Finding 1 — Merge commits bypass the self-review filter, creating an unbounded review loop

**What:** The "don't review your own work" guard matches on commit *subject*
prefix, but `MergeGate` lands every branch with `git merge --no-ff --no-edit`,
which generates the subject `Merge branch 'agent/reviewer-<id>'`. That subject
does not start with `review:`, so the guard misses it and the reviewer is woken
to review its own review.

**Where:**
- `agents/sensors/git.py:12` — `SELF_AUTHORED_PREFIXES = ("review:",)  # the reviewer must not review itself`
- `agents/sensors/git.py:44` — `if subject.startswith(SELF_AUTHORED_PREFIXES)`
- `agents/merge_gate.py:75` — `run_git(self.repo_root, "merge", "--no-ff", "--no-edit", branch)`
- `hooks/post-commit:16` — same subject-prefix test, same gap

**Severity:** high

**Why it matters:** It is a self-sustaining loop that consumes budget and
produces nothing. Each turn of the cycle is:

1. Reviewer commits `review: <sha> ...` on `agent/reviewer-<id>` — correctly filtered.
2. `MergeGate` merges it as `Merge branch 'agent/reviewer-<id>'` — **not** filtered.
3. Hook and/or `GitSensor` publish `commit.pushed` for the merge.
4. Reviewer wakes, finds a commit whose entire diff is a `docs/reviews/*.md` file
   it wrote itself, and writes another review — go to 1.

There is no natural terminator. The dedupe key is the SHA, and every merge has a
fresh SHA, so dedupe does not break the cycle either.

**This is not hypothetical — it has already happened twice in `main`.** Replaying
`GitSensor.poll`'s exact filter over `dd43412..5bd7ab7`:

```
  SKIP  c89f2407  review: dd43412 is an empty commit; no casino/ changes to fix
  EMIT  7ad57a10  Merge branch 'agent/reviewer-ef2360f8'      <- lands only docs/reviews/dd43412.md
  SKIP  5d503b55  review: a5f8628 correctly fixes post-subcommand -v; 3 low findings
  EMIT  5bd7ab79  Merge branch 'agent/reviewer-a4b188f3'      <- lands only docs/reviews/a5f8628.md
```

The two `SKIP` lines are the guard working. The two `EMIT` lines immediately
after are the same content getting through anyway, wearing a merge commit as a
disguise. The review you are reading is turn 3 of that loop, and committing it
will start turn 4.

A secondary cost: these loop-induced reviews are structurally content-free. A
reviewer handed a merge whose only file is a markdown review has nothing in
`casino/` to examine, so it either reports "nothing to do" or reaches for
marginal findings to justify the run. Both are waste; the second is worse,
because it pollutes the deliverable history with manufactured findings.

**Suggested fix (not applied — `agents/` and `hooks/` are outside my write
scope):** subject-prefix matching is the wrong discriminator, because the
subject of a merge is generated by git, not by the agent. Two better options:

- *Dereference the merge.* For a commit with 2+ parents, test the subjects of
  the commits it actually introduces (`git log --pretty=%s <sha>^1..<sha>`) and
  skip when they all match `SELF_AUTHORED_PREFIXES`. Correct for merges that mix
  agent and human work, and keeps genuinely code-bearing merges (e.g.
  `5d25dda`, the test-author merge) flowing through.
- *Match on the changed path set.* Skip any commit whose entire diff falls under
  `docs/reviews/`. Simpler and cheaper, and it closes the loop regardless of how
  the commit was created. Weaker in general, but it maps exactly onto the
  reviewer's declared write scope.

Whichever is chosen, `agents/sensors/git.py` and `hooks/post-commit` must apply
the *same* predicate, or the fast path and the reconcile path will disagree —
the hook would stay silent while the poller still fires, which is harder to
diagnose than the current consistent failure.
