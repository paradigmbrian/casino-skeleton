## 1. The one "what held" claim about the cascade is false, and the code at this same commit shows it

**Where:** `docs/superpowers/specs/2026-08-23-autonomous-agent-layer-design.md:410-414`.
Contradicted by `agents/merge_gate.py:75` and `agents/sensors/git.py:12`.

**Severity: medium.**

The appended section closes with:

> The cascade was observed working end to end: a hook-published commit woke the reviewer, its
> `review:` commit was correctly skipped by the git sensor rather than triggering a
> self-review loop.

The first half is true. The second half is not, and it was already falsifiable when it was
written:

- `MergeGate` merges with `run_git(self.repo_root, "merge", "--no-ff", "--no-edit", branch)`
  (`agents/merge_gate.py:75`). Every accepted run therefore lands **two** commits on `main`:
  the agent's own `review: …` commit and a merge commit subjected
  `Merge branch 'agent/reviewer-<id>'`.
- `GitSensor` at `b8578b7` skips on subject prefix only — `SELF_AUTHORED_PREFIXES =
  ("review:",)` (`agents/sensors/git.py:12`), applied per-line at `:43`, over a `git log
  --reverse` at `:33` with no `--no-merges` and no `--first-parent`. (At HEAD this file has
  since been reworked by `d214795`; the line numbers above are the ones at `b8578b7`.)

So the reviewer's `review:` commit is skipped and the merge commit that carries it is not.
The self-review loop is not closed; it is closed one commit later and reopened by the merge.
Merge commit `7ad57a1` was already in `main`'s history at `b8578b7`, so the counterexample
predates the claim. It was subsequently caught by the layer itself (`a67487e`, "merge commits
bypass the self-review filter") and fixed in `d214795`.

**Why it matters.** This is not a stale-doc nit. The whole value of this commit is that it is
an honest post-mortem — it earns credibility by cataloguing ten defects and five broken rails.
The "What held" paragraph is the one place that says *stop looking here*, which makes it the
most expensive place in the document to be wrong. A reader who trusts it skips exactly the
check that would have found the loop. The correction is one clause: the `review:` prefix
filter holds for the agent's own commit and does not cover the merge commit the gate creates
for it.

## 2. The `†` footnote overclaims, and disagrees with both the commit message and its own correction text

**Where:** `docs/superpowers/specs/2026-08-23-autonomous-agent-layer-design.md:233-241`
(five daggered rows, footnote at 241) versus `:402-408` (the Scope enforcement correction).

**Severity: low.**

Three statements about the same set disagree:

- The commit message says "the **four** safety rails that did not hold as designed."
- Five rows carry `†` (Budget guard, Timeouts and DLQ, Idempotency, Kill switch, Scope
  enforcement).
- The footnote at line 241 reads "These rails did not hold as designed."

The odd one out is Scope enforcement, and its own correction says so:

> Had the design's gate-only rail been the whole story this would not have mattered; because
> the plan advertised prevention *and* detection while delivering only detection, it was worth
> catching.

That is a defect in the **plan's** `can_use_tool` guard, not in the spec's rail. The spec
listed only the gate-side check (line 237: "Diff checked against `write_scope` at the gate,
before tests"), and the gate-side check worked — `MergeGate` still checks scope before tests.
Marking the row "did not hold as designed" says the opposite of what the correction says four
hundred lines below it, and inflates the failure count by one.

**Why it matters.** Lower stakes than finding 1, but the same mechanism: a document whose
credibility rests on precise self-criticism should not be imprecise in the direction of
*more* self-criticism either. Softening the footnote to "These rails needed correction — see
below" and noting on the Scope row that the spec's rail held while the plan's extra guard did
not would resolve all three statements at once.
