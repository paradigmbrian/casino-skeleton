permanent entry in `main`.

**Where:** `dd434125bb87a045f782c65bf3c7485a8dd45814` (whole commit; no file)

**Severity:** low

**Why it matters:** This repo's history is itself a deliverable — `CLAUDE.md` notes
the agent commits "must appear in the history alongside the template's original
`Initial commit`." A reader auditing that history hits a `chore:` commit that
asserts a verification happened but carries no evidence of what was verified or
what the result was. Tooling that walks history per-commit (bisect, changelog
generation, per-commit CI, the `GitSensor` poller) has to tolerate a commit with an
empty changeset. This is cheap to avoid: a hook smoke test can be run against a
scratch branch or a throwaway clone and then discarded, rather than landing on

This is a process/history observation, not a functional bug. Nothing depends on the
commit being absent, and removing it now would mean rewriting pushed history — which
is explicitly not worth it for a low-severity cosmetic issue. **Recommendation: leave
it, prefer a scratch branch for future hook smoke tests.**

## Finding 2 — The verification was incomplete: the hook cannot work inside a git worktree

**What:** `hooks/post-commit` resolves the Python interpreter as
`$(git rev-parse --show-toplevel)/.venv/bin/python`. In a linked worktree,
`--show-toplevel` is the *worktree* root, which has no `.venv`. Hooks are shared
across worktrees via the common git dir, so the hook does run there — and fails.

**Where:** `hooks/post-commit:7-8`

```bash
REPO_ROOT="$(git rev-parse --show-toplevel)"
exec "$REPO_ROOT/.venv/bin/python" - <<'PY'
```

**Severity:** low (see caveats below — it is self-healing and non-blocking)

**Verified from this very worktree:**

```
worktree toplevel:  /Users/brian/Development/casino-skeleton-worktrees/reviewer-ef2360f8
expected venv path: <that>/.venv/bin/python   -> MISSING
git-common-dir:     /Users/brian/Development/casino-skeleton/.git
core.hooksPath:     (unset -> worktrees use the common-dir hook)
```

The `.venv` exists only at `/Users/brian/Development/casino-skeleton/.venv`.

**Why it matters:** The agent layer commits from inside worker worktrees (see
`feat(agents): write-scope predicate and git worktree lifecycle`). Those are exactly
the commits the reviewer most wants to be woken by, and they are the ones where the
fast-path `commit.pushed` publish silently does not happen. Commit dd43412 was made
in the main checkout, where `.venv` resolves fine — so it exercised the one path that
was already working and left the worktree path unverified. The commit message reads
as a blanket "hook verified" when the coverage was partial.

**Caveats that keep this low, not high:**
- `post-commit` is a notification hook; git ignores its exit status, so a failure
  here cannot break or roll back a commit. Worst case is stderr noise.
- The hook's own header comment anticipates gaps: the `GitSensor` poller reconciles
  missed commits, and the dedupe key is the SHA, so recovery is automatic and
  duplicate delivery is harmless. The effect is added latency on worktree commits,
  not lost events.

**Suggested fix (not applied — outside my write scope):** resolve the venv from the
common dir rather than the worktree, e.g.
`REPO_ROOT="$(dirname "$(git rev-parse --git-common-dir)")"`, and/or fall back to
`command -v python3` when `$REPO_ROOT/.venv/bin/python` is not executable.

`hooks/` is outside my write scope (`casino/`, `docs/reviews/`), so I did not touch
it. Note also that `hooks/post-commit` was not yet tracked at dd43412 — it was added
two commits later in `20a4cea`. So at the moment this "verify" commit was authored,
the hook it verified existed only as an untracked local symlink.
