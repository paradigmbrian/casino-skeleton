# Review: 1497888 — fix(agents): recover from a hard exit instead of deadlocking

Reviewed at HEAD `5d25dda`. The commit under review is three commits back, so where a
later commit already addressed something I say so rather than re-reporting it as live.

**The core diagnosis is right and the fix is the right shape.** The dedupe index
(`idx_tasks_inflight ON tasks(dedupe_key) WHERE state IN ('queued','leased')`) genuinely
does make an abandoned `leased` row a permanent block on that unit of work, `lease()`
genuinely only selects `state='queued'`, and nothing reclaimed. `reclaim_expired_leases`
is the correct local analogue of an SQS visibility timeout, the dead-letter branch on
`attempts >= max_attempts` is right, and clearing `leased_at` on reclaim is right. The
tests added are the tests I would have asked for.

What follows is what the fix does not cover.

---

## 1. `recover()` is unconditionally destructive, and nothing stops a second supervisor from running it

**Where:** `agents/supervisor.py:49-64` (`recover`), called from `agents/supervisor.py:197`
(`run`). Enabling context: `agents/cli.py:84-93` (`up`) and
`agents/supervisor.py:215-217` (`build_default_supervisor`).

**Severity: high.**

`recover()`'s docstring justifies itself with "no run can be in flight in a process that
has not started yet." That is true of *this* process and says nothing about any other. All
three recovery steps are global writes against shared state, with no scoping to the caller:

- `reclaim_expired_leases(timeout_s=0, ...)` — cutoff is *now*, so it matches every leased
  row regardless of age, including one a live supervisor leased a second ago.
- `close_dangling_runs()` — `UPDATE runs ... WHERE ended_at IS NULL`, i.e. every currently
  executing run, marked `interrupted` with the error string "supervisor exited before this
  run finished."
- `park_orphans()` — at HEAD this walks `git worktree list` and retires everything under
  `WORKTREE_ROOT`. A live agent's checkout is registered there, so it gets
  `worktree remove --force`'d out from under the running agent, and if that agent has not
  committed yet, `retire` → `cleanup` also runs `git branch -D` on its branch.

There is no PID file, no `flock`, no advisory lock, no "already running" check anywhere in
`agents/` (I grepped). `agents up` twice — two terminals, a tmux pane forgotten from
yesterday, a supervisor under a process manager that restarts it before the old one has
exited — and the second process's first act is to sabotage the first: requeue its task,
falsely record its in-flight run as interrupted, and delete its working directory mid-edit.
The reclaimed task then gets picked up concurrently in the other process (see finding 2).

This is a genuine increase in blast radius introduced by this commit. Before it, a second
`agents up` was mostly wasteful — the lease serialized the two processes. Now startup is an
active destructive operation.

**Why it matters:** the commit is about surviving an unclean exit. It makes the *clean*
concurrent case worse than it was, and the failure is silent and data-destroying rather
than a deadlock you can see in `agents status`.

**Suggested direction (not applied — outside my write scope):** take an exclusive
`flock` on a file in `STATE_DIR` in `cli.py`'s `up` branch (or at the top of
`Supervisor.run`) and exit with a clear message if it is held. That also gives `recover()`
the precondition its docstring already assumes.

## 2. Lease reclaim has no fencing token, so a reclaimed-but-still-live task can be settled twice

**Where:** `agents/adapters/sqlite_store.py:179-197` (`reclaim_expired_leases`),
`agents/adapters/sqlite_store.py:165-177` (`ack`/`nack`), swept from
`agents/supervisor.py:174-175` (`_dispatch_loop`).

**Severity: medium.**

`lease()` records no holder identity — just `state='leased'` and a timestamp. `ack(task_id)`
and `nack(task_id, ...)` are blind writes; neither checks that the caller still owns the
lease. So once the mid-flight sweep in `_dispatch_loop` reclaims a lease whose worker is
actually still alive, two slots hold the same task and whichever finishes *last* decides
the task's final state.

I ran this against the real store:

```
reclaimed: ['8de8408c773f']
second lease is same task: True   attempts: 2
after slot A acks (merged):   {'queued': 0, 'leased': 0, 'done': 1, 'dead': 0}
after slot B nacks:           {'queued': 0, 'leased': 0, 'done': 0, 'dead': 1}
```

A task that merged successfully ends up recorded as dead-lettered. Both agents also ran a
full worker execution against the same event and both reached the merge gate.

The AWS mapping this is modelled on does not have this hole: SQS pairs the visibility
timeout with a *receipt handle*, and `DeleteMessage` with a stale handle is rejected. This
change took the timeout and left the fence behind. `docs/aws-mapping.md:24` describes
`ack` → `DeleteMessage` as if the correspondence were exact.

How likely is expiry under a live worker? `agents/config.py:27-29` justifies
`LEASE_TIMEOUT_S = 900` as "comfortably above the longest `WorkerSpec.timeout_s` (420s)
plus a gate cycle." That accounting is incomplete: `execute` also waits on `self._gate_lock`,
which serializes the gate across `MAX_CONCURRENT_WORKERS`, and each gate cycle runs the
full `pytest` suite in a fresh worktree. So the real ceiling is 420s + up to two full suite
runs + merge, and the suite's runtime is unbounded and grows with the repo. 900s is a
margin, not a guarantee, and it silently erodes as tests are added.

**Suggested direction:** add a `lease_token` column set by `lease()` and required by
`ack`/`nack`'s `WHERE` clause; a settle whose token no longer matches is a no-op and worth
a `LOG.warning`. Cheap, and it makes the timeout tuning non-safety-critical.

## 3. `close_dangling_runs` writes to the DB but not the JSONL ledger, which is the artifact it exists to protect

**Where:** `agents/adapters/sqlite_store.py:254-266` (`close_dangling_runs`), versus
`agents/adapters/sqlite_store.py:207-226` (`record`). Stated motivation:
`agents/ports.py:57-59`.

**Severity: medium.**

`record()` writes the `runs` row *and* appends to `self.ledger_path`. `close_dangling_runs`
issues a raw `UPDATE` and never touches the ledger. `tests/agents/test_run_store.py:59`
(`test_every_record_is_mirrored_to_the_jsonl_ledger`) shows the mirror is a deliberate
invariant; this commit adds the first write path that breaks it.

Verified:

```
closed:   ['r1']
DB says : interrupted  2026-08-24T01:36:39.561527+00:00
LEDGER  : r1  dispatched  None
ledger lines: 1
```

The irony is in the port docstring, which justifies the method as "the ledger stops being
reconstructable" — the ledger is exactly what does not get fixed. `agents status` reads the
DB and says `interrupted`; anyone reconstructing history from `runs.jsonl`, which the README
presents as the append-only audit trail and `docs/aws-mapping.md:28` maps to CloudWatch Logs,
still sees `dispatched` with a null `ended_at`. The two sources of truth now disagree, and
the JSONL one is the one you would reach for after the machine is gone.

**Suggested direction:** have `close_dangling_runs` read the full rows, apply the change,
and route the result through the same ledger-append path `record()` uses — or extract that
append so both callers share it.

## 4. `recover()` reports dead-lettered work as "reclaimed"

**Where:** `agents/supervisor.py:55-58`, `agents/adapters/sqlite_store.py:197`.

**Severity: low.**

`reclaim_expired_leases` returns one flat list of ids for two very different outcomes:
requeued (will run again) and dead-lettered (silently dropped). Its sibling `nack` returns
`'requeued'` or `'dead_lettered'` precisely because that distinction matters. `recover()`
then logs `"reclaimed %d abandoned lease(s)"` for both, so a restart that permanently
discarded two units of work prints the same reassuring line as one that recovered them.

Given the whole point of this commit is that work was disappearing silently, the log line
that would tell an operator it happened again is the one that hides it. Returning
`dict[str, str]` (id → outcome), or two lists, would fix it. Note this would require
updating `tests/agents/test_work_queue.py:86-113`, which asserts the flat-list shape — I
can't touch `tests/`, so flagging rather than changing.

## 5. An interrupted run's record can point at a branch `recover()` just deleted

**Where:** ordering within `agents/supervisor.py:54-64`.

**Severity: low.**

`close_dangling_runs()` runs before `park_orphans()`. The closed record keeps its `branch`
field (e.g. `agent/reviewer-3f2a1b`), but `park_orphans` → `retire` deletes any branch with
zero commits ahead of main. So after recovery, `agents status` can show an `interrupted` run
naming a ref that no longer resolves. It is defensible — there is nothing on that branch to
read — but the README's promise that `git log agent/<worker>-<id>` shows what an agent tried
does not hold for this class of record, and there is no signal distinguishing "branch
deleted, was empty" from "branch missing, something is wrong."

## 6. (Already fixed downstream) `park_orphans` originally `rmtree`'d arbitrary directories

**Where:** `agents/worktree.py:52-78` as landed in this commit.

**Severity: was medium — remediated by `acb29e2`, no action needed.**

Recording it because it bears on the commit as reviewed. The original implementation walked
`worktree_root.iterdir()` and treated every directory as a checkout. `WORKTREE_ROOT/integration`
— the merge gate's container directory (`agents/supervisor.py:223`), not a worktree — would
match, `git rev-parse` in it would fail, `branch` would be `""`, so the `if branch and ...`
guard fell through to `self.park(wt)`, whose `shutil.rmtree` fallback deletes the directory
outright. Any unrelated directory a user parked under `WORKTREE_ROOT` would go the same way.
`acb29e2` replaced the filesystem scan with `git worktree list --porcelain` plus a
`relative_to` containment check, which is the correct approach.
